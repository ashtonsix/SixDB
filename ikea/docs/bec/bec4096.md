# Using Bec4096

Bec4096 encodes an `ikea::bitset4096` of 4096 positions (sixteen 256-position
blocks) into one headless body of at most 548 bytes. The caller retains one
population, exact byte length and address per body. A reader decodes the
body's block directory once; afterwards it can decode one block, count a
block's bytes or rank a position without decoding the other blocks.

[Using Bec](usage.md) states the lifecycle shared with Bec256 (association,
binding, read windows, checked and prepared writes, publication) and when to
choose each variant. This guide covers what is specific to Bec4096.

## Representation

A body is four parts, concatenated least-significant bit first with no gaps.
The only padding is zero high bits in the final byte. Populations 0 and 4096
are determined and have zero-byte bodies.

| Part | Contents | Bits |
| --- | --- | --- |
| Raw mask | Bit k set when block k is stored raw | 16 |
| Raw blocks | Each raw block's 256 plain bits, in block order (byte aligned: byte 2 + 32j for the j-th) | 256 each |
| Head | The top four split levels of the 4096-position bisection tree (regions of 4096, 2048, 1024 and 512 positions), breadth-first, with Bec256's split law, over the population minus the raw blocks' counts; it recovers every other block's population and counts raw blocks as empty | ≤ 146 |
| Length table | For blocks 0–14: the block's stream length as `length − min(c)` in `bit_width(min(max(c), 256) − min(c))` bits, where `min`/`max` are the exact fewest and most stream bits for block population `c` | ≤ 120 |
| Block streams | Each coded nonterminal block's [Bec256 stream](representation.md), in block order, **bit-aligned**: a stream starts wherever the previous one ended | ≤ 256 each |

A block is stored raw when its byte-rank widths sum to at least 144 bits or its
Bec256 stream would exceed 256 bits, so incompressible blocks cost their plain
size and every coded stream is at most 256 bits. The split law stores a left count minus its lower bound in
`bit_width(min(p, 2h − p))` bits for parent count `p` and half size `h`.
Populations 0, 1, 255 and 256 need no length bits, empty, full and raw blocks
have no stream, and block 15's length is never needed. The `min`/`max` tables
are in `detail/bec4096.h`; the check derives them independently. The caller's
population is always the value's true total; binding counts the raw blocks.

Binding derives a **directory** from the mask, raw blocks, head and length
table: each block's population, the bit offset of its stream (or raw bytes),
and the raw mask. It is reusable access
state held by the reader, not part of the body.

## Encode, bind and read

The [example](../../examples/bec/bec4096.cpp) sets four positions, encodes them
in eight bytes at offset 3, and reads one block, its byte counts and ranks:

```cpp
namespace bc = ikea::bec4096;
auto size = bc::encode(bits, population, plane, 3, effects);
auto input = bc::bind_reader(std::span(storage).subspan(3), *size, population);
ikea::bitset256 block;
bc::decode(*input, 1, block);                 // block 1 alone
std::array<std::uint8_t, 32> counts;
bc::counts(*input, 1, counts);                // its byte populations
unsigned before = bc::rank(*input, 301);      // set positions before 301
unsigned inside = bc::population(*input, 256, 256);
```

| Call | Work | Output overlap with the body |
| --- | --- | --- |
| `decode(reader, bitset4096&)` | All blocks: one fused walk | Not allowed |
| `decode(reader, block, bitset256&)` | One block's stream | Allowed |
| `counts(reader, block, span<uint8_t, 32>)` | One block's count tree, no rank fields | Allowed |
| `counts(reader, span<uint8_t, 512>)` | Every block's count tree | Not allowed |
| `rank(reader, position)`, `population(reader, first, count)` | Block totals from the directory, then one block's tree and at most one byte rank per end | — |

Coordinates are trusted and asserted: `block < 16`, `position ≤ 4096`,
`first ≤ 4096` and `count ≤ 4096 − first`. Byte-span overloads
(`span<byte, 512>`, `span<byte, 32>`) are the canonical little-endian bridge.

Block access decodes nothing outside its block, but it is not physical
isolation: a block's 64-byte read window starts at its stream inside the body
and may load neighbouring streams' bytes (never decoding them), and count-only
reads may load rank bytes they do not interpret. Every load stays within the
reader's granted span. Exact body spans are always sufficient; a readable
suffix after the body lets the last blocks' windows load directly.

`encode` prepares all sixteen streams before its first store, so its input may
overlap the destination, as with Bec256. Changing one block changes its stream
length and moves every later stream: Bec4096 replaces whole bodies; there is no
block-local mutation.

## Native blocks

On NEON and AVX-512 profiles, `<ikea/bec/author/bec4096.h>` exposes blocks of a
reader as Bec256's native values:

```cpp
namespace bn = ikea::bec256::native;
auto both = ikea::bec4096::native::read_pair(x, 3, y, 3); // block 3 of x, then of y
auto kept = bn::intersection(both, bn::load_pair(mask));    // a 512-bit plain mask
unsigned in_x = bn::population(bn::part<0>(kept));
auto byte_counts = ikea::bec4096::native::counts(x, 7);     // bn::block of counts
```

`read_pair` takes one block from each of one or two readers (low half, then
high half), decoding both chains together. Empty and full blocks return filled
values without decoding. The values feed Bec256's Boolean, population and
encoding bodies; there is no separate 512-byte native aggregate.

## Execution

Block streams are unchanged Bec256 streams, so Bec4096 enters Bec256's kernels
at an arbitrary bit. The two variants share one level step,
`detail::{neon,avx512}::level<Half, Active, Domain>`: each stream owns `Domain`
lanes, the first `Active` holding a level's nodes. Bec256 runs one or two
streams per vector; Bec4096 packs all sixteen streams densely through the four
upper block levels (16, 32, 64 and 128 nodes), then runs Bec256's leaf and rank
kernels two blocks at a time. Groups with fewer than five nonterminal blocks
decode block by block instead. Encoding reuses Bec256's byte counts
(`encode_counts`), packs blocks independently and emits the exact body. A
block whose byte-rank widths sum to 144 bits or more (Calico's shortcut) is
stored raw without encoding; any other block whose stream exceeds 256 bits also
goes raw. Against deciding by exact stream length this costs no bytes: raw
blocks also drop their length field and head share.

Resident measurements with retained readers are summarized in
[choosing a variant](usage.md#choose-a-variant). Builds without NEON or the
AVX-512 profile, including AVX2-only x86, use portable paths built on Bec256's
scalar codec: correct on the supported little-endian profiles, measured at
1.1–1.4× the scalar Bec256 control, untuned.
