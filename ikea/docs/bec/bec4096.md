# Using Bec4096

Bec4096 encodes an `ikea::bitset4096` of 4096 positions (sixteen 256-position
blocks) into one headless body of at most 784 bytes. The caller retains one
**population**, the exact byte length and the address per body, instead of
sixteen of each for Bec256 blocks. A reader can materialize one block, count
the bytes of a block, or rank a position without decoding the other blocks.

Include `<ikea/bec.h>` (or `<ikea/bec/bec4096.h>`) and link `ikea::bec`. The
vocabulary is Bec256's: `encode`, `encoding`, `const_view`, `bind_reader`,
`reader`, `decode`, `view`, `journal` and `error`. Read the
[Bec256 guide](bec256.md) for the shared write, admission and effects rules;
this guide covers what differs.

## Representation

Bec4096 is Bec256's bisection tree extended to 4096 positions, laid out so each
block stays separately reachable. All fields are least-significant bit first
with no gaps; the only padding is zero high bits in the final byte.

1. **Head.** The top four split levels (regions of 4096, 2048, 1024 and 512
   positions), breadth-first, using Bec256's split law: store the left count
   minus its lower bound in `bit_width(min(p, 2h − p))` bits. They recover the
   sixteen block populations. At most 146 bits.
2. **Length table.** For blocks 0–14, the block's stream length in bits, stored
   as `length − min(c)` in `bit_width(max(c) − min(c))` bits. `min` and `max`
   are the exact fewest and most bits of a Bec256 stream with population `c`
   (`detail/bec4096.h`; the check derives them independently). Populations 0,
   1, 255 and 256 need no bits; block 15's length is never needed.
3. **Blocks.** Each nonterminal block's [Bec256 stream](representation.md), in
   block order, bit-packed without byte padding. Empty and full blocks have no
   stream.

Populations 0 and 4096 have zero-byte bodies, distinguished by the caller's
population. Bodies of dense random data are slightly larger than sixteen Bec256
bodies (head and length table against Bec256's byte padding); with the
caller's metadata counted they are much smaller. Across 14 RealRoaring families
the [Bec4096 study](../../../workbench/spikes/bec4096/README.md#storage) measured
30.7 bytes per 4096 positions with packed parent metadata, against 56.3 for
sixteen Bec256 bodies with a packed directory.

## Encode, bind and read

The [example](../../examples/bec/bec4096.cpp) sets four positions, encodes them
at offset 3, and reads one block, its byte counts and ranks:

```cpp
namespace bc = ikea::bec4096;
auto size = bc::encode(bits, population, plane, 3, effects);
auto input = bc::bind_reader(std::span(storage).subspan(3), *size, population);
ikea::bitset256 block;
bc::decode(*input, 1, block);                 // one block
std::array<std::uint8_t, 32> counts;
bc::counts(*input, 1, counts);                // its byte populations
unsigned before = bc::rank(*input, 301);      // set positions before 301
unsigned inside = bc::population(*input, 256, 256);
```

`encode` checks population, destination capacity and effect capacity before
any store and writes the exact body with one issued-span effect. Input may not
overlap the destination. `encoding::make` prepares the body without owner
writes when the owner must wait between preparation and publication, exactly
as for Bec256.

`bind_reader` validates the complete body once (head, lengths, every block
stream, padding and length) and retains a 64-byte **frame**: each block's
population and stream position. `reader::population(block)` and every later
access use that frame and never reread the head. `bind_reader_unchecked`
decodes the frame without validation for callers that already hold a content
proof; it still reads the head.

| Call | Work |
| --- | --- |
| `decode(reader, bitset4096&)` | All sixteen blocks; the fused walk below |
| `decode(reader, block, bitset256&)` | One block's stream only |
| `counts(reader, block, span<uint8_t,32>)` | One block's count tree, no rank fields |
| `counts(reader, span<uint8_t,512>)` | Every block's count tree |
| `rank(reader, position)`, `population(reader, first, count)` | Block totals from the frame, then one block's tree and at most one byte rank per end |

Byte-span overloads (`span<byte,512>` and `span<byte,32>`) are the canonical
little-endian bridge, as with Bec256.

## Execution

Block streams are unchanged Bec256 streams, so Bec4096 enters Bec256's kernels
at an arbitrary bit. The two codecs share one level step,
`detail::{neon,avx512}::level<Half, Active, Domain>`: each stream owns `Domain`
lanes, the first `Active` holding a level's nodes. Bec256 runs one or two
streams per vector; Bec4096 packs all sixteen streams densely through the four
upper block levels (16, 32, 64 and 128 nodes) and then runs Bec256's leaf and
rank kernels two blocks at a time. Groups with fewer than five nonterminal
blocks decode block by block instead. Encoding reuses Bec256's byte counts
(`encode_counts`), packs blocks independently and emits the exact body with
register-carried merges.

On a native profile (NEON, or AVX-512 with Bec256's required features) the
study measured full decode at 0.50–0.55× of sixteen Bec256 decodes on Zen 5 and
0.83× on Neoverse V2, rank at 0.66–0.83×, single-block reads at parity, and
encode near parity on dense groups. Other builds, including AVX2-only x86, use
a portable path built on Bec256's scalar codec: correct, not tuned.

## Memory access bounds

An exact body span suffices for every call. As with Bec256, granting at least
64 initialized readable bytes after the body lets native reads load each
block's window directly; without it, streams near the end of the body are
copied into zeroed scratch (1–20% slower full decode in the study). The
encoder writes only the exact body.

## Mutation

Replacing a body replaces its population, length and possibly its address,
like any Bec256 replacement; see [coordinating a replacement](bec256.md#coordinate-a-replacement-with-its-metadata).
Changing one block inside a body changes that block's stream length and moves
every later stream, so Bec4096 re-encodes the whole body. Block-local
mutation is not provided.
