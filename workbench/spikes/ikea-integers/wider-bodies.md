# Wider bodies: extension and locality

2026-09-09 proposal, followed by the [width-56 experiment](wide56/README.md) on
2026-09-10. Width 56 now has exact native encode/decode, point/get16 and direct
sum implementations; that experiment records actual access widths and timings.
The other wider native codecs remain proposals. The
[locality audit](locality/README.md) establishes geometry independently of
implementation and performance; [spike results](README.md) also cover the
separate narrow kernels.

## What the full-width prior actually does

Calico's [planes.h](../../../../calico/workbench/prototypes/bytepack/planes.h)
stores native 1/2/4-byte planes over 256 values, followed by the residual
bit-packed tail. Its first two whole bytes are separate leading planes;
subsequent whole bytes are grouped in ascending powers of two.

| Logical width | Plane widths, high to low |
| ---: | --- |
| 12 | 8 + residual 4 |
| 24 | 8 + 8 + 8 |
| 40 | 8 + 8 + 8 + 16 |
| 56 | 8 + 8 + 8 + 32 |
| 64 | 8 + 8 + 16 + 32 |

The width-56 point read therefore loads bytes at `i`, `256+i`, `512+i`,
and the four-byte word at `768+4*i`. This avoids seven-byte AoS expansion,
but value zero already touches four widely separated lines. Removing two
leading planes still leaves separate 8- and 32-bit body planes. A local
tail alone cannot repair that parent geometry.

A read-only compilation of the prior with Linux Clang 21.1.8, `-O3`, and
AVX2, Granite Rapids, and Neoverse V2 target settings confirmed this point
sequence. Its full-width get16/get256 retain runtime `Shape` traversal and
outlined width helpers, even when a wrapper supplies a constant shape.
They zero the u64 output, then traverse planes and repeatedly shift and OR
into that output. Bulk branches contain native widening operations, but
the enclosing materializing API retains traversal, dispatch, and repeated
output traffic. These are code-generation observations, not hardware timings.

The prior's [contextual findings](../../../../calico/workbench/prototypes/bytepack/evidence/context.md)
also distinguish full reconstruction from selective reconstruction and
progressive filtering. That API is useful prior art and a comparator; its
overhead is not an appropriate ceiling for a new native body kernel.
Future comparisons should state the width knowledge, output type, and
materialization work each endpoint receives. An immediate native consumer
and an API that fills u64 arrays perform different work.

## Proposed body representation and compute seam

For `w = k - h = 8*q + r`, retain the proposed eight-value packet:
`8*q` little-endian whole-body bytes in per-value AoS order, followed by
`r` bytes of the LocalPack tail. The packet occupies exactly `w` bytes.
An optional, deliberately separate filter head is an explicit resource.

Implement body expansion by byte count and native lane width, independently
of the tail and repetition count. Whole-body widths 1/2/4/8 bytes have direct
load or widening paths. Widths 3/5/6/7 use generated byte-shuffle indices.
Join the expanded body and decoded low tail as `(body << r) | tail`; head
reconstruction, when requested, is a separate part of the authored read.

Use u16 lanes for a 12-bit consumer, u32 for a 24-bit consumer, and u64 where
needed. A materializing u64 adapter can provide the prior's output contract
without making u64 the universal native carrier. Keep scalar point reads
separate: exact overlapping scalar loads can assemble the selected body's
`q` bytes, then combine its tail. A bulk decoder should not call that point
reader once per value.

## Generalizing the width-56 result

The [width-56 experiment](wide56/README.md#data-and-native-work) now owns the
implemented seven-byte expansion, inverse packing, exact instruction accesses
and native-fragment contract. Its [measurements](wide56/README.md#hardware-findings-2026-09-10)
replace the initial unmeasured candidate routes. AVX-512 requires BW+VBMI for
that path; an AVX-512 label alone is insufficient.

Some of the byte-window reasoning extends without selecting new kernels.
For four u64 outputs and a body width `q` of 5, 6 or 7 bytes, two 16-byte
windows at offsets 0 and `4*q-16` cover exactly `4*q` input bytes. Generated
lane-local shuffle indices can widen their values. A 3-byte body targeting
u32 lanes can similarly decode eight values from windows at 0 and 8. The
inverse needs exact final stores too; decode geometry alone does not establish
encode throughput. Native implementation and hardware comparisons for these
other widths remain open.

## Operation grain and head choice

An eight-value data packet does not require an eight-value call boundary.
For u64 values, the useful native consumer grain can be eight lanes on
AVX-512, four on AVX2, or two on NEON. An inline bulk loop can decode and
consume those chunks while reusing constants. A logical get16 can visit
the same chunks or materialize them explicitly. This avoids requiring all
sixteen u64 values to cross every stage boundary as a large aggregate.
If a consumer must retain the entire group, its register pressure and
handoff are a separate probe.

The [exact dense-packing proof](locality/README.md#why-some-wider-dense-groups-cannot-be-repaired-by-permutation)
applies to the remaining payload width `w`. Every Local8 point fits within
two adjacent lines. Dense aligned groups of sixteen fit at every reachable
uniform-run phase exactly when `w <= 32 + gcd(w,32)`.

| Logical width | Head 0: remaining width | Head 8 | Head 16 |
| ---: | ---: | ---: | ---: |
| 12 | 12, passes | 4, passes | unavailable |
| 24 | 24, passes | 16, passes | 8, passes |
| 40 | 40, passes | 32, passes | 24, passes |
| 56 | 56, fails | 48, passes | 40, passes |
| 64 | 64, passes | 56, fails | 48, passes |

Head-zero width 56 consumes 112 bytes per group. Its group starts reach
phases 0, 48, 32, and 16; phases 48 and 32 require three lines. This is
an exact-density limitation, not a decoder defect. A 16-byte pad per group
would restore the bound but consume the same payload storage as raw u64;
padding remains a separate, unselected placement. Conversely, removing an
8-bit head from width 64 changes a passing 128-byte group at phase zero
into this failing 112-byte case. A smaller body is not automatically a
better aligned-group layout.

The exception applies only to a **deliberately separate filter head**.
Ordinary high bytes do not disappear from the payload bound merely because
they are named heads or stored in separate planes. Head reads and storage
must still be counted in full reconstruction and whole-operation measurements.

The bounded experiment asks whether these native body paths preserve the
locality guarantees while achieving strong encode and decode throughput
with actual consumers and L2-sized working sets. Exact final stores, shuffle
throughput, register pressure, and the benefit of wider execution are examined
in the [width-56 follow-up](wide56/README.md). There is no need to introduce a TU
for each extent or a general metadata framework to answer that question.
